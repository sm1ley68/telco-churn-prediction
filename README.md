# 📉 Прогнозирование оттока клиентов телеком-компании

Проект по бинарной классификации на датасете **Telco Customer Churn** (IBM, 7043 клиента): модель предсказывает, уйдёт ли клиент. Классы несбалансированы (~26.5% оттока), поэтому accuracy здесь обманчива — основной фокус сделан на **precision / recall / ROC-AUC** и осознанном подборе порога классификации. Помимо предсказательной модели, проект включает EDA, сегментацию клиентов через K-Means и интерактивное демо на Streamlit.

## 🎯 Задача и мотивация

Удержать существующего клиента дешевле, чем привлечь нового, поэтому для телеком-компаний отток (churn) — одна из ключевых бизнес-метрик. Если заранее выявить клиентов с высоким риском ухода, отдел удержания может адресно предложить им скидку, апгрейд или более выгодный контракт.

Главная особенность задачи — **дисбаланс классов**: уходит лишь ~26.5% клиентов. Модель, которая всегда предсказывает «останется», получит accuracy ≈ 73%, но будет абсолютно бесполезной — она не найдёт ни одного уходящего. Поэтому ставка делается на метрики, чувствительные к классу меньшинства, и на recall-ориентированный порог: **пропустить уходящего клиента дороже, чем поднять ложную тревогу.**

## 📊 Данные

- **Источник:** [Telco Customer Churn](https://github.com/IBM/telco-customer-churn-on-icp4d) (IBM Sample Data)
- **Объём:** 7043 клиента, 21 признак
- **Целевая переменная:** `Churn` (Yes/No) — баланс классов **73.5% / 26.5%**
- **Признаки:** демография (пол, наличие партнёра, иждивенцев), параметры подписки (тип контракта, интернет, доп. сервисы), биллинг (`tenure`, `MonthlyCharges`, `TotalCharges`, способ оплаты)

## 🔧 Подход / Pipeline

1. **EDA** — анализ распределений, доли оттока в разрезе контракта и срока обслуживания.
2. **Чистка данных** — починка `TotalCharges`: 11 строк содержали пробел вместо числа (это новые клиенты с `tenure = 0`), значения приведены к числу и заполнены нулём.
3. **Кодирование** — one-hot для категориальных признаков (`drop_first=True`), 21 → 31 столбец.
4. **Baseline** — `DummyClassifier(strategy='most_frequent')` как точка отсчёта.
5. **Модель** — `RandomForestClassifier`, стратифицированный train/test split 80/20.
6. **Валидация** — 5-фолдовая стратифицированная кросс-валидация (ROC-AUC).
7. **Подбор порога** — снижение порога классификации с 0.5 до 0.3 ради recall.
8. **Сегментация** — кластеризация клиентов через K-Means (метод локтя + silhouette).
9. **Деплой** — компактный `Pipeline` (препроцессинг + модель) на Streamlit Cloud.

## 📈 Ключевые результаты

> **Важно:** в [живом демо](https://telco-churn-sm1ley.streamlit.app) развёрнута компактная модель на **8 признаках** (ROC-AUC ≈ 0.80), тогда как полная аналитическая модель на всех признаках даёт ROC-AUC ≈ 0.825. Поэтому числа в шапке и в демо немного отличаются — это разные модели, а не ошибка.

Оценка аналитической модели (`RandomForestClassifier`, 30 признаков) на отложенной тестовой выборке (1409 клиентов):

| Метрика    | Baseline (Dummy) | RandomForest |
|------------|:----------------:|:------------:|
| Accuracy   | 0.7346           | **0.7850**   |
| Precision  | —                | 0.6179       |
| Recall     | —                | 0.4973       |
| F1         | —                | 0.5511       |
| ROC-AUC    | —                | **0.8253**   |

**5-фолдовая стратифицированная кросс-валидация (ROC-AUC):** **0.8217 ± 0.0112** — стабильное качество без признаков переобучения на конкретном разбиении.

### ⚠️ Почему accuracy обманчива

Baseline, который всегда отвечает «клиент останется», даёт accuracy **0.7346** — просто потому, что 73.5% клиентов действительно не уходят. RandomForest поднимает accuracy всего до **0.785**, и на первый взгляд прирост скромный. Но accuracy игнорирует главное: насколько хорошо модель ловит именно **уходящих** клиентов — а ради них всё и затевается. Поэтому опорные метрики здесь — **recall** (какую долю уходящих мы поймали) и **ROC-AUC** (0.8253), не зависящий от выбранного порога.

### 🎚️ Подбор порога классификации

При стандартном пороге 0.5 модель ловит лишь половину уходящих. Так как бизнес-цена пропущенного клиента выше цены ложной тревоги, порог снижен до **0.3**:

| Порог | Recall | Precision |
|:-----:|:------:|:---------:|
| 0.5   | 0.508  | 0.615     |
| 0.3   | **0.746** | 0.522  |

Снижение порога поднимает recall с 0.508 до **0.746** — модель находит ~3 из 4 уходящих ценой умеренного падения precision. Для задачи удержания это выгодный размен.

> **О задеплоенной модели.** В демо используется упрощённый `Pipeline` на 8 интерпретируемых признаках с `class_weight='balanced'` (для удобного ручного ввода в интерфейсе). По кросс-валидации он показывает ROC-AUC **0.8014 ± 0.0082**, recall **0.4896 ± 0.013**, precision **0.5827 ± 0.0138**; в приложении к нему также применён порог 0.3.

## 👥 Сегментация клиентов (K-Means)

Кластеризация по `tenure`, `MonthlyCharges`, `TotalCharges` (число кластеров выбрано по методу локтя и silhouette-анализу). Получены **4 сегмента** с заметно разной долей оттока:

| Сегмент | Размер | tenure (мес) | MonthlyCharges ($) | Доля оттока | Бизнес-смысл |
|---------|:------:|:------------:|:------------------:|:-----------:|--------------|
| 🔴 Группа риска (высокий чек) | 2276 | 15.4 | 80.8 | **48%** | Зона максимального риска |
| 🟠 Недавние эконом           | 1703 | 10.2 | 31.8 | 25%        | Умеренный риск |
| 🟡 Лояльные премиум        | 1904 | 59.5 | 93.3 | 15%        | Долгие клиенты с высоким чеком |
| 🟢 Лояльные эконом         | 1160 | 53.6 | 34.9 | **5%**     | Самый стабильный сегмент |

Главный вывод сегментации: риск концентрируется среди **недавно пришедших клиентов с высоким месячным платежом** — их почти половина уходит. Именно этот сегмент стоит приоритизировать в кампаниях удержания.

## 💡 Выводы

- **Тип контракта — сильнейший фактор оттока.** Помесячный контракт: **42.7%** оттока, годовой — **11.3%**, двухлетний — всего **2.8%**. Перевод клиента на долгосрочный контракт радикально снижает риск ухода.
- **Срок обслуживания (tenure) важен.** Ушедшие клиенты в среднем были с компанией **18.0 месяцев** против **37.6 месяцев** у оставшихся — отток смещён к началу жизненного цикла клиента.
- Эти два инсайта согласуются с сегментацией: самый «текучий» кластер — это как раз новички (низкий tenure) на помесячных тарифах с высоким чеком.

## ⚙️ Как запустить локально

```bash
# 1. Клонировать репозиторий
git clone https://github.com/sm1ley68/telco-churn-prediction.git
cd telco-churn-prediction

# 2. Установить зависимости
pip install -r requirements.txt

# 3. Запустить Streamlit-приложение
streamlit run app.py
```

Приложение откроется в браузере по адресу `http://localhost:8501`. Для воспроизведения всего анализа откройте `telco_churn_prediction.ipynb`.

## 🔮 Возможные улучшения

- **Переобучение под конкретную компанию.** Модель обучена на публичных данных одного телекома; в продакшене её следует переобучать на данных конкретной компании — поведение клиентов и факторы оттока отличаются от рынка к рынку.
- **Больше признаков.** Добавление поведенческих данных (обращения в поддержку, история платежей, использование сервисов) потенциально повысит качество.
- **Градиентный бустинг.** XGBoost / LightGBM / CatBoost обычно превосходят RandomForest на табличных данных — логичный следующий шаг.
- **Подбор гиперпараметров.** Систематический поиск (GridSearch / Optuna) вместо параметров по умолчанию.
- **Калибровка вероятностей** для более надёжного бизнес-порога и оценки ожидаемого эффекта удержания.
